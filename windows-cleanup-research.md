# Windows temporary files and cache cleanup research

Researched 6 September 2026. Intended for a Windows cleaning-program developer.

This catalogue maps Windows temporary storage, regenerable caches, diagnostic files, managed cleanup operations and important exclusions. It focuses on Windows 10/11 desktops and selected Microsoft applications/enterprise features. **There is no fixed universal list of every Windows cache**: builds, installed components, application versions, policies and user configuration change the locations. Windows itself provides cleanup handlers, while apps can put temporary data in custom locations.

The accompanying JSON is a **research catalogue, not an executable deletion manifest**. Every rule starts disabled. `discover_only` entries require more target-specific investigation, and `exclude` entries are deliberately protected. No cleanup has been executed; these rules have not been tested on Windows in this session.

## What the evidence supports

Microsoft documents the storage semantics and supported cleanup/repair mechanisms. Community cleaner source provides additional observed paths, not a guarantee that its deletion policy is appropriate. Forum posts were used to identify omissions and failure modes, then checked against primary documentation where available. Recommendations such as 7-day temp retention and 30-day diagnostic retention are this report's conservative design suggestions, not Microsoft guarantees.

Three particularly useful findings:

- Resolve actual temporary directories. SYSTEM can use `SystemTemp` or `C:\Windows\SystemTemp`, while a normal user follows different environment resolution. Do not discover all targets by calling the temp API once from an elevated cleaner. [GetTempPath2](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-gettemppath2a)
- Packaged-app `LocalCache` is persistent across sessions and can contain authentication tokens; `TemporaryFolder` has different lifetime semantics. A generic `Packages\*\LocalCache` purge is unjustified. [ApplicationData](https://learn.microsoft.com/en-us/uwp/api/windows.storage.applicationdata?view=winrt-28000)
- Windows Installer and Configuration Manager caches are managed stores. The presence of “cache” in their name does not make raw deletion valid. [Installer cache](https://learn.microsoft.com/en-us/troubleshoot/windows-client/application-management/missing-windows-installer-cache), [Configuration Manager](https://learn.microsoft.com/en-us/intune/configmgr/core/clients/manage/configure-client-cache)

## Reading the catalogue

Paths are discovery hints, not commands. `%LOCALAPPDATA%` and `%APPDATA%` belong to the selected user, which can differ from the administrator executing your program. `%SystemRoot%`, `%ProgramData%` and `%SystemDrive%` must be resolved rather than hard-coded. `{...}` denotes a resolver your application must implement; it is not literal Windows syntax.

A source marked “community path” confirms that a maintenance project has used that path. It does not provide a supported Windows API contract. A “conservative exclusion” is a design decision to avoid destructive generalization. The JSON retains these distinctions per rule.

All age values below are suggested minimum days since last write. A dash means no universal age rule is proposed. Optional caches generally need a complete owner-approved clear rather than an arbitrary age-based purge of database fragments.

## Recommended program architecture

Use distinct actions for ordinary temporary-file cleanup, optional regenerable caches, diagnostic retention, user content/history, and repairs. This prevents a “clean everything” button from silently resetting apps or removing repair evidence.

### Discover Windows cleanup capabilities at runtime

Inspect the installed handlers under:

```text
HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Explorer\VolumeCaches
```

Handler availability and display names differ by build, installed features and language. A handler may use COM logic rather than a static folder rule. Do not assume a `Folder` registry value is permission to remove the directory or that every handler shares the same registry format. Use the Windows cleanup manager or implement the documented interfaces carefully. [Microsoft handler documentation](https://learn.microsoft.com/en-us/windows/win32/lwef/disk-cleanup)

Categories to look for include Temporary files, Temporary Internet Files, Thumbnails, DirectX Shader Cache, Delivery Optimization Files, Windows Update Cleanup, system error dumps/minidumps, WER reports, Setup log files, Temporary Windows installation files, Previous Windows installation(s), Device driver packages, Downloaded Program Files, and Recycle Bin. Treat them as semantic categories, not guaranteed registry key names. Do not automatically select every discovered handler.

### Supported commands to dispatch selectively

These are reference operations, not a script to run in sequence:

| Purpose | Command / interface | Integration condition |
|---|---|---|
| Configure a Disk Cleanup selection | `cleanmgr.exe /sageset:123` | Interactive setup of selected categories; use a profile number owned by your application. |
| Run that selection | `cleanmgr.exe /sagerun:123` | Not a dry run. `/sagerun` enumerates drives; `/d` does not constrain it. |

### File deletion engine requirements

These are engineering recommendations for this program, not claims that Microsoft prescribes this exact architecture.

1. **Resolve and validate roots.** Get the Windows directory using system APIs; resolve user Known Folders with the selected user's token. Discover registered profiles rather than assuming `C:\Users\*` covers everyone. Skip special/default profiles unless your product explicitly handles them. Resolve redirected locations without following arbitrary junctions. A missing variable must never collapse into a drive-root wildcard. Reject roots equal to a drive, profile, Windows directory, ProgramData, or other protected ancestor.
2. **Separate the UI from privileged deletion.** A service running as SYSTEM must not blindly accept a user's path or environment variable. Use allowlisted rule IDs and independently resolve the permitted roots. Respect profile ownership and the user's selected scope.
3. **Treat reparse points as boundaries.** Skip junctions, symlinks, mount points and cloud placeholders. A one-time path check is insufficient: another process can swap a directory between scan and delete. An elevated implementation needs handle-based identity validation and protection against directory traversal races; fail closed if this is unavailable. [Reparse-point behavior](https://learn.microsoft.com/en-us/windows/win32/fileio/reparse-points)
4. **Select individual files.** Do not recursively remove an old directory just because the directory's timestamp is old. Validate each child and remove only empty subdirectories afterwards. Keep the top-level temp folder, owner and ACLs intact. Deduplicate nested roots and file IDs so scan totals and deletion counts remain meaningful.
5. **Skip live work.** Use an age filter, but also avoid active installers, servicing, uploads, office recovery and running owner apps. A successful delete or an unlocked file does not prove it was unused: a process can allow deletion while holding a handle, or expect to reopen the file later. Skip errors instead of killing processes, taking ownership, altering permissions or scheduling deletion on reboot.
6. **Do not decide “update idle” from one signal.** Check Windows Update/servicing state, active jobs, pending restart indicators and known deployment activity. Treat uncertain system servicing state as a reason to skip those categories, not the whole scan. Never delete `pending.xml`, rename system stores, or stop update services simply to make ordinary cleanup succeed.
7. **Report accurate outcomes.** Separate candidate bytes, eligible bytes, deleted logical bytes and observed free-space change. Hard links, compressed/sparse files, deduplication and open delete-pending handles can make these differ. Log skipped/failed entries and command exit codes. Keep diagnostic inventories private to the relevant machine/user.
8. **Version and test every adapter.** Match OS build/app version, architecture, installation type, profile format and relocated cache settings. Unknown versions should fall back to reporting or owner cleanup. Ship rule updates independently, pinned to reviewed versions; never download and execute an unreviewed community rule database.

A useful first release would implement selected-user stale temp cleanup plus Windows-managed cleanup categories. Add diagnostic retention next. Keep app resets, update repairs, search/font/icon rebuilds and privacy erasure on distinct screens.

### Minimum validation before enabling deletion

The supplied JSON was syntax-checked and its source references checked for consistency; **no Windows integration tests were run here**. Before enabling rules in the program, use disposable Windows VMs to test normal and redirected profiles, spaces/non-ASCII paths, multiple users, SYSTEM vs user temp resolution, 32-bit redirection, missing variables, active files, and junctions introduced between scan and deletion. Use known sentinel files outside the allowed roots to detect traversal. Verify all selected apps can launch and that Windows Update and MSI repair still work. For a repair adapter, test the actual failure/recovery sequence separately from cleanup.

## Extending coverage beyond Windows

The broadest reusable starting point found is [Winapp2](https://github.com/MoscaDotTo/Winapp2), a large community catalogue. [BleachBit documents its integration](https://docs.bleachbit.org/doc/winapp2ini.html). Use these as research indexes for application adapters; their entries include privacy state and aggressive rules as well as caches. Review upstream licensing before incorporating code or definitions. This report does not reproduce those databases or endorse bulk execution.

Third-party GPU caches, Chrome/Firefox profiles, developer package caches, game launchers, Adobe caches, Office versions, OEM installer extraction folders and server-role storage need separate product-specific inventories. Likewise, RAM standby lists, ARP/neighbor tables, credential tickets and other memory caches are not disk-junk directories. Do not advertise a disk cleaner as improving performance merely by making all caches empty.

For each additional app, record executable/version detection, profile/cache resolver, exact cache kind, supported purge API, effects, active-work exclusions, and a tested fixture. Keep user-created downloads, offline content, savegames, databases and recovery files protected.
